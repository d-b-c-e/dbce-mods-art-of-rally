## What the toolkit comparison actually shows

The mod already consumes toolkit native FFB/input and managed Forza telemetry.
The **managed force model is still local**. Dbce.Wheel.Ffb.dll is vendor/test-only;
the release allowlist deliberately excludes it.

The 640-row unsmoothed grid and 63-row smoothing block helped find earlier upstream
profile/clamp defects. They do not establish equivalence of the combined chains:

- Mod: lateral force/trail → gain/invert → speed fade → hard clamp → EMA.
- Pinned v0.8.0 SimLite: lateral force/trail → EMA → gain/invert → speed fade → hard clamp
  (its other shaper effects are disabled).

The executable regression loads the pinned DLL, maps its opposite force sign,
and evaluates 23,000 N followed by zero at a constant 40 km/h, zero slip,
reference 11,500, Strength 50 and Smoothing 0.2. Results are **0.80 then 0.16**
for the mod, **1.00 then 0.32** for the toolkit. Those are normalized outputs.
Clipping and filtering do not commute even at steady speed; changing speed is
another source of divergence. Earlier “negligible, steady-speed-equivalent” wording
was not an adequate basis for adopting the model.

Do wrapper/GUID adoption first, with an explicit solution for the native module
name and shared lifecycle. Treat force-model migration as an equivalence project
or an intentional retune with its own test window. Apply user strength only once.

## Test framework and release boundary

The framework is documented in [PRE-RELEASE-TESTING.md](../PRE-RELEASE-TESTING.md).
It executes arithmetic/save regressions, production camera/watchdog/capture logic
with test doubles, pinned native diagnostics and ABI checks, vector regeneration,
payload/installer tests, and negative evidence-gate tests. It rejects empty runs.

The optional recorder captures bounded value-type arrays during driving and saves
only when idle or after shutdown releases outputs. Offline replay re-evaluates
force inputs and checks timing evidence, without driving any hardware. Incomplete,
truncated or altered recordings fail validation. It cannot recreate the game,
prove force delivery, or verify rendered pixels. Captures from synthetic tests are
explicitly separate from attended evidence.

Reviewed the cruisn-collection task history and its current recording/replay files.
MAME's `.inp`, machine state and frame clock are emulator facilities, not reusable
Unity APIs. We adopted build hashes, immutable cases, settings snapshots, completion
receipts and separate evidence per run. Full game input replay is future work.

**Still untested here:** packaged UMM load/upgrade, real Unity/Harmony callback
installation, camera visuals, cold/new-stage stutter, rig force release/reacquisition,
learned-input persistence across game restarts, live support module inspection,
telemetry consumers and recorder performance in the game. Fanatec, PS5-attached
T300 and RWD snapback follow-up remain hardware-specific open items.

The automated report and generated manual checklist refer to one exact zip.
The manual gate requires all seven attended cases, tester/rig, notes and hashed
evidence. No release or real-game deployment is performed by this review.
